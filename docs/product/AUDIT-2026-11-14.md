# Product readiness audit — 2026-11-14

**Question.** The project has taken many paths. Is it pointed at a consumer-facing product — a plausible
replacement for Hermes Agent that works the same way for the user — and if not, what has to change?

**Scope.** Every tracked file (165), the seven `plugins/`, the `scripts/` tree (8,089 lines), the live
`dsh-personal` host (read-only), the installed DSH 0.2.2-rc.2 runtime and its docs. Three independent
audits (code, distribution, user journey) were run against this evidence and their findings were re-checked
by hand; the P0 items below are the ones I verified personally.

**Verdict in one line:** the substrate and the engineering discipline are right; the product is not started.
What exists is a well-documented, single-user homelab deployment plus the kit to rebuild it with an AI
agent. A consumer product needs the opposite centre of gravity: one install, one first conversation, one
place to see and correct memory, one update path — and a channel you actually message.

| Dimension | Score | Meaning |
|---|---:|---|
| Consumer product | **2/10** | Nothing a non-technical person can install, open and use. |
| Technical kit | **7/10** | Pieces are pinned, tested, documented; assembly still needs an expert + an agent. |
| Research / evidence | **9/10** | The engineering record is unusually rigorous and honest. |
| **Direction** | **⚠ pivot required** | Keep DSH; rebuild the wrapper around the user journey, not more capability. |

## 2. What genuinely works

These are real assets, not claims:

1. **A running, always-on assistant host** with a hardened systemd user unit, telemetry egress disabled,
   journald sink, token/cost meter, digest and alerting — all verified in `research/m0-*.md`.
2. **Identity at prompt order 0** (`@local/dsh-soul`): small, tested, cache-safe, file-based.
3. **A correctly shaped memory layer** (`@local/dsh-memory-personal`): a bounded, inspectable curated block
   with hard character budgets that force consolidation, plus three tools; ~40 tokens when empty, fail-open,
   zero dependencies. This is the Hermes memory mechanism, well executed — after the fix in §4.
4. **Session recall** via the official FTS5 bundle — durable SQLite, on-demand, no LLM cost.
5. **A real security posture**: prompt-injection corpus 4/4, egress observe + alert, restore drill 20/20,
   secret-shaped-string CI scan, plugin admission ledger with sha512 and rollback.
6. **MCP connectors** through rc.2's official `mcp-manager`, including one working capability surface.
7. **The UI seam research** (`research/ui-primitives-slots.md`, `ui-design-brief.md`): verified slots,
   tokens and an AA-contrast design system that a product can reuse.

The discipline behind those is rare and should survive the pivot.

## 3. What is not what it looks like

| Presented as | Reality at audit |
|---|---|
| "Identity, memory, recall, push and heartbeat are live" (README) | Identity and recall are live. Push is inert without `NTFY_URL`. Heartbeat is default-OFF. Memory had never been exercised live. |
| "Session recall + long-term memory" | Long-term memory has two clients installed and one disabled; the enabled client is the new one, unproven in the real UI. |
| "A personal AI assistant" | A Web UI that requires choosing a workspace, a browser tab, and a login — no messaging channel. |
| "Security: no secrets in logs" | The PWA auth proxy mints owner cookies for any tailnet client (deployment only, but it is the current remote-access story). |
| "Public build log / reference for your own agent" | Accurate — and the front door's first H2 is still "Build your own with your DSH agent". A consumer sees an engineering blog, not a product. |
| "M2 complete" | Curator, retention, backups are real; proactivity visible to a user is not. |

Two structural facts explain most of the gap:

- **The product surface is missing.** Hermes is defined by a long-lived gateway you message from your phone.
  There is no channel here: `@xmanrui/dsh-im` is on HOLD (#547 breaks final-answer delivery), and no
  replacement has been built. A Web UI you open is a tool, not an assistant.
- **The install surface is missing.** There is no root `package.json`, no installer, no profile bundle, no
  uninstaller. The documented onboarding is "point your own DSH agent at this repo" — which is a novel
  distribution model, but not a consumer one.

## 4. P0 findings

### P0-1 — Memory writes were invisible until restart (fixed)

`plugins/dsh-memory-personal/index.js` captured the rendered block as a **string** at `apply()` and registered
it as a static prompt section. DSH resolves a section's `text` **per request** when it is a function
(`dsh-system-prompt/lib/index.js:389`) but not when it is a string. Consequence: `memory_remember` wrote the
file and told the model "it is in the prompt block from the next request", while the block stayed frozen until
the Host restarted — potentially weeks for an always-on assistant. `memory_forget` had the same defect, so a
"forgotten" fact stayed in the prompt.

**Status: fixed and regression-tested.** The section now passes `text: () => profileSectionText(path)`, a
failed read degrades to an empty block, and the selftest asserts that a write is visible and a forget is gone
in the same process. This also makes the two memory tiers behave as designed instead of only-on-restart.

### P0-2 — The PWA auth proxy grants owner to any tailnet client (deployment only)

`scripts/dsh-pwa-autologin-proxy.mjs` defaults `DSH_AUTOLOGIN_ALLOW` to empty, which it logs as
`allow=any tailnet client`. It reads the Host's launch token from journald/logs, exchanges it for a signed
owner cookie, and does so for every request and WebSocket upgrade. It is active now
(`dsh-pwa-autologin-personal.service`, tailnet `:8454` → proxy `:7007`). On a shared tailnet, every device and
every tailnet user becomes the owner with no identity check.

**Action:** do not carry this mechanism into the product. For the homelab, set a non-empty
`DSH_AUTOLOGIN_ALLOW` (or remove the proxy) — a host change that needs your approval. The consumer product
needs a supported auth path, not a token-minting proxy.

### P0-3 — Connector OAuth silently enables write-capable SaaS tools

`plugins/dsh-capabilities/composio.js:369-385` creates a Composio session that enables **all** managed-OAuth
toolkits (Gmail, Slack, Stripe, Drive, …) with `execute.enable_multi_execute: true`, registers it as an MCP
server, and exposes the tools to the model as ordinary calls. There is no per-tool scope narrowing, no
read-only default, and no approval gate. This is a direct "agent can send mail / move money" path, one
capability class above what a consumer product should ship enabled.

**Action:** default to read-only toolkits, require explicit per-connector consent, and route write actions
through DSH approvals. Until then it is a homelab experiment, not a product feature.

### P0-4 — Memory is a long-lived prompt-injection channel with no user-visible control

Entries the model writes are injected verbatim into the system prompt inside `<memory_profile>` tags, with no
injection/exfiltration scan and no provenance. A poisoned fact read from a web page or email can become
standing instructions on every later request — the highest-leverage attack on an assistant that remembers.
The existing injection corpus tests tool abuse, not memory poisoning across sessions. `memory_forget` also
removes only the curated entry; Hindsight retains the fact and its derived observations.

**Action:** scan/stage writes (approve or quarantine suspicious entries), keep provenance, show a memory
browser with delete, and state the erasure contract in the UI. `research/m2-retention-policy.md` has the
right analysis; the product needs the controls.

### P0-5 — There is no installable artifact

No root `package.json`, no installer, no frozen profile bundle, no uninstaller. All seven plugins are
`"private": true`, version `0.1.0`, with no `license`, `engines`, or `repository`; they are linked by absolute
path. `scripts/setup-personal-profile.sh` is hardcoded to `/home/josh/projects/DSH-playground`,
`homelab.taildace6c.ts.net`, port 7002, `tailscale serve`, and copies credentials from an unrelated DSH home.

**Action:** this is not a bug to patch; it is the product to build. See `DIRECTION.md` §5–§7.

### P0-6 — The defining Hermes surface is absent

No Telegram/Discord/Signal/email channel works. The channel is the product's front door, its approval surface
and its proactivity delivery path. Everything else in this repo is infrastructure for a surface that does not
exist yet.

**Action:** make the channel the first product milestone, not a later integration.

## 5. P1 findings (consumer blockers)

**Distribution and packaging**

- DSH is a developer preview: 169 breaking-change rows across the upgrade guides; every bump is a re-vet.
  Pin the runtime and own the upgrade path behind a release gate.
- `dsh plugin` requires pnpm on `PATH`; a consumer must never run pnpm. Ship a prebuilt profile bundle.
- No code signing, notarization, updater, uninstaller, or diagnostics bundle.
- No aggregated third-party notices. An MIT wrapper may redistribute DSH (include the copyright/permission
  notice); Apache-2.0 dependencies also want their NOTICEs. No DeepSeek marks imply endorsement.

**Onboarding and UX**

- No first-run wizard: provider key or account login, persona (name/tone), "what may it do", channel setup,
  privacy choices.
- `SOUL.md` is hand-edited prose followed by a restart. No in-product identity editing.
- No memory browser, no "what do you remember", no delete control; `forget.sh` is a shell script.
- No assistant settings. The only panels are Host control (restart the service), Capabilities (admin), and
  Profiles (two hardcoded homelab URLs) — operator tools, not consumer surfaces.
- Approvals are the stock Web dialog and exist only in the browser; no channel round-trip.
- The Web UI requires choosing a workspace before the composer works — wrong default for a chat-first
  assistant.
- No troubleshooting, support, or "first conversation" page. Zero product screenshots are tracked.

**Proactivity and retention**

- Heartbeat is default-OFF and needs an env var; push is inert without `NTFY_URL`; the digest is a 0600 file.
  A user sees zero unprompted messages, so the assistant does not feel present.
- Push used to forward the session title (derived from the first user message) to the push provider. Fixed
  in this pass: payloads now carry only a short session id and event kind.
- Daily backups include `.credentials.yaml` in plaintext (0700 tree); only the separate off-site script
  encrypts. A consumer product should use the OS keychain and an encrypted-by-default backup.

**Testing and operations**

- Tests: 30 heartbeat, 8 soul, 21 memory checks, 7 capabilities. Nothing covers `dsh-push`,
  `dsh-host-control`, `dsh-profiles`, the autologin proxy, or any `scripts/` logic beyond `bash -n`.
  CI now runs the capabilities tests (added in this pass) because it previously did not.
- The live profile directory accumulates hand-made `.bak-*` files (eight at audit time). No migration or
  cleanup discipline.
- Plugin home fallbacks disagreed (`~/.dsh-personal` vs `~/.dsh`); fixed to DSH's own default.

**Docs and identity**

- Five competing stories: engineering log, build recipe for an AI agent, homelab deployment, B2B
  productised-services business (an excluded local doc — never published), and a retired UI track. The
  engineering log wins by volume.
- Bilingual coverage is 14 of 78 docs, with a CI hash gate. It doubles maintenance on a moving log while the
  pages a consumer needs do not exist. Keep the checker; apply i18n to the five product pages, not the
  research archive.
- The private business doc argues **against** a general-purpose consumer assistant and **against** self-serve
  SaaS, and recommends paid productised services. That is a legitimate strategy, but it is the opposite of
  this instruction. The two cannot both be the plan.

## 7. Consolidation: five paths, one product

The repo does not need more capability paths; it needs a centre of gravity.

1. **Engineering log → keep, but demote.** It is a credibility asset and a hiring/lead asset. It is not the
   product and should not be the first thing a user sees.
2. **Build recipe for AI agents (`agents/`) → keep as a secondary, builder-facing path.** It is genuinely
   novel and useful, but it is not onboarding.
3. **Homelab deployment (systemd, tailscale, nftables, Hindsight) → keep as a reference deployment.** Do not
   ship it as the consumer install. A consumer cannot run nftables or a shared Postgres.
4. **B2B productised services (`research/business/`, excluded from git) → park.** It contradicts the consumer
   direction and should not steer engineering until a business decision is made.
5. **UI experiments → keep the design system, delete the admin panels from the consumer surface.** Host
   control, Profiles and Capabilities are operator/B2B tools. The product needs Identity, Memory, Activity
   and Settings.

**Keep as product IP:** `dsh-soul`, `dsh-memory-personal`, the identity/memory policy documents, the design
tokens, the injection corpus and the admission discipline.
**Keep as kit/ops:** backup, restore drill, egress observe, telemetry digest, admission ledger.
**Do not ship:** autologin proxy, host-control, profiles switcher, Composio all-toolkit session, guizang
(AGPL-3.0), media-desk, tailnet/nftables/systemd assumptions.
**Rewrite:** channel (own bridge or a fixed upstream), push (local-first, no third-party by default),
heartbeat (scheduled + delivered, user-configurable), packaging (frozen bundle + shell/installer).

## 8. Readiness gates for a consumer v1

A stranger must be able to do all of the following without a terminal, root, an AI agent, or reading
`research/`:

1. Install one signed artifact on macOS or Windows (Linux optional) and open it.
2. Complete first-run: model access, name/tone, one channel, privacy choices — under five minutes.
3. Send a message from their phone and get a correct answer with an approval round-trip.
4. Ask "what do you remember?", see the entries, correct one, and have the correction take effect in the
   same session.
5. Receive one useful unprompted message that they can turn off.
6. Update to a new pinned DSH release from inside the app; roll back if it fails.
7. Uninstall and delete all data, with a plain-language explanation of what was stored where.
8. Read a one-page trust page: what leaves the machine, what is stored, what is never sent.

No gate is green today. Gates 1–3 are the product spine; 4–8 are what make it a *consumer* product rather
than a demo.

## 9. Decisions required

| # | Decision | Recommendation |

| D15 | **What is the product?** A general personal assistant (Hermes-class) or a narrow vertical harness (business doc)? | Commit to the general personal assistant; park the B2B doc until after v1. The consumer direction is now explicit. |

| D20 | **Licensing/branding.** | MIT wrapper, own name/marks, no DeepSeek marks; drop AGPL content plugins from the distributed product; add `THIRD-PARTY-NOTICES`. |
