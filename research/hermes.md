# Hermes Agent — architecture, features, and lessons for DSH

Research note for turning DSH into a personal AI assistant. Based on the **real local install** at `~/.hermes` (source checkout `~/.hermes/hermes-agent`, install-stamp `0.23.0`, commit `2bd378e`, MIT), inspected read-only on 2026-11-09, plus the official docs — whose source is the same `website/docs/` tree published at [hermes-agent.nousresearch.com/docs](https://hermes-agent.nousresearch.com/docs/). Local observations are labelled "local install"; no personal memory, session, or secret content is reproduced — mechanism only.

## What it is / positioning

Hermes Agent is Nous Research's open-source (MIT) **always-on personal agent**: one agent core across a CLI, a long-lived messaging gateway, a TUI, an Electron desktop app, and editor integrations. The pitch is "the self-improving AI agent" — it creates skills from experience, improves them, nudges itself to persist memory, searches its own past conversations, and builds a model of the user across sessions; it is built to live on a $5 VPS or GPU box, not your laptop, so you can talk to it from Telegram while it works elsewhere ([README](https://github.com/NousResearch/hermes-agent#readme), [architecture](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture)). Two invariants shape the design: per-conversation **prompt caching is sacred** (no mid-session system-prompt mutation), and the **core is a narrow waist** — new capability arrives as a plugin, skill, CLI command, or service-gated tool, never as new core surface (`hermes-agent/AGENTS.md`).

## Runtime architecture & entrypoints

- **Entry points:** `cli.py` (interactive CLI), `gateway/run.py` (long-running messaging gateway), `acp_adapter/` (Agent Client Protocol for VS Code/Zed/JetBrains over stdio JSON-RPC), `hermes_cli/` subcommands (`hermes` = setup/model/tools/gateway/cron/memory/skills/plugins/…), batch runner, API server, Python library. All converge on one `AIAgent` ([architecture](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture)).
- **One agent core, platform-agnostic.** `run_agent.py` is a thin facade; the turn loop lives in `agent/conversation_loop.py` + `agent/turn_*.py` phases. `AIAgent` owns prompt assembly, provider/API mode selection (`chat_completions` / `codex_responses` / `anthropic_messages`), interruptible model calls, tool dispatch (sequential or thread-pool parallel), retries/fallback, compression, persistence ([agent loop](https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop)).
- **Prompt assembly is tiered:** stable (identity/`SOUL.md`, tool guidance, skills index) → context (project files, memory) → volatile (timestamps, ephemeral notices). Skills use progressive disclosure; memory is a frozen snapshot; the prompt is cached byte-for-byte for the session.
- **Tools self-register at import:** every `tools/*.py` calls `registry.register()` at import time; `model_tools.py` collects schemas and dispatches with plugin hooks/middleware. Local tree has 54 register calls in tool modules; docs count 70+ tools and ~28 toolsets. `hermes_state.py` is a facade + `hermes_state_*.py` siblings (god-file → topic modules) — a layout worth copying.

## Messaging / gateway layer

- **A long-running process hosting 25+ platform adapters as plugins** — Telegram, Discord, Slack, WhatsApp (Baileys bridge and Cloud API), Signal, Matrix, Mattermost, Email (IMAP/SMTP), SMS/Twilio, iMessage (BlueBubbles), Teams, Google Chat, IRC, LINE, DingTalk, Feishu, WeCom, Weixin, QQ, and more (`plugins/platforms/*/adapter.py`; local tree has 26 adapter dirs). Adapters are lazily imported, each normalizes inbound events into a `MessageEvent`, and implements `connect/send`.
- **Routing:** session key `agent:{namespace}:{platform}:{chat_type}:{chat_id}` (threads/topics appended), built only via `build_session_key()`; profile multiplexing puts `{profile}` in the namespace so one gateway process serves several isolated profiles ([gateway internals](https://hermes-agent.nousresearch.com/docs/developer-guide/gateway-internals)).
- **Busy handling:** two-level guard — adapter queues + interrupt event; the runner intercepts `/stop`, `/new`, `/queue`, `/status`, `/approve`, `/deny` while the agent runs. A durable session FIFO with admission records plus steer/redirect RPCs keeps turns ordered and recoverable after crashes.
- **Authorization is default-deny:** per-platform allow-all flag → platform allowlist → DM pairing (8-char crypto codes, 1 h TTL, rate limits, lockout) → global allowlist → global allow-all → deny.
- **Delivery:** direct reply, home-channel delivery, explicit targets (`telegram:<chat_id>[:thread]`, `discord:#channel`, …), cross-platform fan-out (`all`, `origin,all`). `channel_directory.json` caches reachable channels/contacts per platform (~5 min refresh) so friendly names resolve for `send_message` and cron delivery. `bot_relay/` is plain file plumbing (`roster.json`, `outbox/`, `replies/`, `claimed/`) for Desktop-relayed agent-to-agent messages across gateways — the gateway half uses no network sockets.
- **Background work rides the gateway:** cron tick, session housekeeping, memory flush, cache refresh, and completion watchers for `terminal(background=true)` processes; hooks fire on `gateway:startup`, `session:start/end/reset`, `agent:start/step/end`, `command:*`. Local install: the gateway reports Telegram + an HTTP API adapter + one custom platform plugin, with another adapter retrying and one fatal (port conflict) **while the gateway and other adapters stay healthy** — adapter failures are isolated, not process-fatal.

## Scheduling / proactivity (cron)

- **Cron jobs are first-class agent tasks, not shell jobs.** `~/.hermes/cron/jobs.json` (atomic temp+rename writes) stores id, name, prompt, `schedule` (`{kind: cron|interval|once, expr, display}`), `skills[]`, `deliver`, `repeat`, `state`, `enabled`, `next_run_at`, `last_*`, model/provider pins, `workdir`, `paused_reason`. Local install: 16 jobs, 11 enabled / 5 paused; delivery targets origin (7), telegram (5), local (3), all (1); one job attaches skills.
- **The gateway ticks the scheduler every 60 s** (file lock prevents double ticks). Each due job gets a **fresh `AIAgent` with no history**, attached skills injected in order, the prompt run to completion, the final response delivered, then metadata and `next_run_at` updated ([cron internals](https://hermes-agent.nousresearch.com/docs/developer-guide/cron-internals)).
- **Durability is taken seriously:** `executions.db` ledger (claimed → running → completed/failed/unknown, `scheduled_instant` identity, progress heartbeats, restart reconciliation) and `deliveries.db` queue with write-back (`delivery_queued` → `ok` / `delivery_failed` / unknown). Failure streaks, one-alert incidents keyed by normalized error signature, catch-up windows for missed occurrences, automatic retries when the model was unreachable, and "park the job while the provider quota window is closed".
- **Pre-dispatch validation** checks provider key, skill requirements, delivery targets, and MCP servers before any LLM call; a misconfigured job becomes `blocked_config` and **spends no tokens**.
- **Model resolution:** per-job pin → `cron.model` fleet default → main model at fire time. The agent can create/edit/pause/remove jobs via `cronjob_manage`, but cannot point a job at a different model (user-owned), and cron runs cannot recursively create jobs unless `cron.allow_agent_scheduling: true`. `no_agent` script jobs run a script on schedule with zero LLM.
- **Proactivity beyond cron:** `/heartbeat` (one recurring prompt re-entering the *current* session when idle, cache-safe) and `/goal` (Ralph-style continuation with an auxiliary judge, completion contracts, and deterministic quality gates) — see [heartbeat](https://hermes-agent.nousresearch.com/docs/user-guide/features/heartbeat) and [goals](https://hermes-agent.nousresearch.com/docs/user-guide/features/goals).

## Memory system

- **Two bounded, curated files:** `MEMORY.md` (agent's notes, 2,200 chars ≈ 800 tokens) and `USER.md` (user profile, 1,375 chars ≈ 500 tokens), injected as a **frozen snapshot at session start** (preserves the prompt cache; new entries appear next session) with a `§`-delimited entry format and a live capacity header ([memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)).
- **The agent edits memory through a tool** (`add`/`patch`/`remove`, `target: memory|user`; no read action). Character limits are hard: an overflow returns an error plus current entries and the exact number of chars to free, so the model must consolidate in one batch before retrying. Duplicates are rejected; entries are scanned for prompt-injection/exfiltration patterns before acceptance.
- **Hygiene:** `memory.write_approval` stages writes for `/memory pending|approve|reject`; a background **self-improvement review fork** runs after turns (~every `nudge_interval` turns), re-reads the conversation and stages memory/skill updates; `display.memory_notifications` controls the chat line. Memory only pays off across session boundaries — hence `/new` at natural boundaries, then `session_search` for recall.
- **Session search is the unbounded tier:** `session_search` runs SQLite FTS5 over all sessions with no LLM calls (discovery/scroll/browse shapes); memory is the ~1,300-token always-in-context tier, FTS5 the unlimited on-demand tier. `/journey` visualizes everything learned over time.
- **External memory providers** are single-select plugins behind a `MemoryProvider` ABC (`sync_turn`, `prefetch`, `shutdown`, `post_setup`): Honcho, Hindsight, Mem0, Supermemory, RetainDB, ByteRover, etc., shipped through the plugin catalog. Local install runs the `hindsight` provider (bank id, `auto_retain`, `auto_recall`, `retain_every_n_turns`, `recall_budget`, recall score/token caps) alongside the built-ins.

## Skills + curator

- **Skills are on-demand procedural memory** following the open [agentskills.io](https://agentskills.io/specification) standard: `~/.hermes/skills/<category>/<name>/SKILL.md` with YAML frontmatter (name, description, version, `platforms`, tags/category, `fallback_for_toolsets`/`requires_toolsets` conditional activation, `required_environment_variables`, `config` settings), plus `references/`, `templates/`, `scripts/`, `assets/`, `examples/`.
- **Progressive disclosure in three levels:** `skills_list()` index (~3k tokens) → `skill_view(name)` full `SKILL.md` → `skill_view(name, path)` one reference file. Every skill is also a `/<skill-name>` slash command; up to 5 chain; **skill bundles** (`~/.hermes/skill-bundles/*.yaml`) group several under one command without touching the prompt cache.
- **The agent writes its own skills** via `skill_manage` (create/patch/write_file/remove_file/delete) with an advisory linter, `/learn` to author a skill from a doc/URL/book, project-local skills (`.hermes/skills`, `.agents/skills`, trust-gated + scan-quarantined), and external skill dirs.
- **Skills Hub:** install from official optional skills, skills.sh, well-known endpoints, GitHub taps, ClawHub, LobeHub, browse.sh, or a raw URL — always through a security scanner with trust tiers (`builtin`/`official`/`trusted`/`community`); `--force` cannot override a `dangerous` verdict; installs record source URL + content hash + scanner version in `.hub/lock.json`.
- **The curator is background skill maintenance** ([curator](https://hermes-agent.nousresearch.com/docs/user-guide/features/curator)): inactivity-triggered (not cron), deterministic `active → stale (14 d) → archived (30 d)` transitions, `~/.hermes/skills/.usage.json` telemetry (use/view/patch counts), opt-in LLM consolidation into umbrellas, pinned/locked skills, per-mutation audit ledger with content-addressed blobs, snapshot backups + rollback, and "never delete, only archive". Local install: curator enabled, 168 h interval, 14/30-day thresholds; 436 installed `SKILL.md` across 44 categories plus `.hub/`, `.archive/`, `.usage.json` — the self-improvement loop has clearly been running.

## Tools / MCP / toolsets

- **Toolsets group tools and map to platforms:** `web`, `search`, `x_search`, `vision`, `video`, `image_gen`, `video_gen`, `computer_use`, `terminal`, `skills`, `browser`, `cronjob`, `file`, `tts`, `todo`, `memory`, `session_search`, `connections`, `project`, `bot_room`, `desktop_ui`, `clarify`, `code_execution`, `delegation`, `kanban`, plus `hermes-*` bundles per surface (`hermes-cli`, `hermes-cron`, `hermes-telegram`, `hermes-gateway`, …). Per-platform toolset selection is user config (`platform_toolsets`); `tools.tool_search.defer` hides rarely used schemas behind on-demand loading.
- **Terminal backends:** local, Docker, SSH, Modal, Daytona, Vercel Sandbox, plus plugin backends (Singularity). Browser: local Chromium/CDP, cloud providers, Computer Use MCP ecosystem.
- **MCP client** ([mcp](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp)): stdio, Streamable HTTP, SSE; OAuth 2.1 (PKCE, DCR/CIMD, device-code, paste-back), mTLS, per-server `include`/`exclude` glob filters, `lazy` start, idle/lifetime recycling, sampling, `trust` levels, per-tool `tool_costs` + per-chat `spend_limit`, tool names prefixed `mcp_<server>_<tool>`, invisible Unicode TAG stripping on results, and a curated `optional-mcps/` catalog (66 entries locally). Local install has 2 configured MCP servers.
- **Plugins are the extension story:** kinds are general, memory-provider, model-provider, context-engine, image-gen, delegation, platform-adapter, terminal-backend, and more; general plugins get hooks (`pre_tool_call`, `post_tool_call`, `pre/post_llm_call`, `on_session_start/end`), tools, and CLI subcommands through a `ctx` API. The **plugin catalog** (`plugin-catalog/*.yaml`, 1,053 entries locally) is the only out-of-tree discovery system, with mandatory 40-hex SHA pins, human-merged PRs, and a `removed.yaml` kill list.

## Delegation / subagents

- **`delegate_task` spawns child `AIAgent`s with a fresh conversation**, their own task_id/terminal session, the parent's toolsets minus child-blocked tools (`delegate_task`, `clarify`, `memory`, `send_message`, `cronjob`), and a focused prompt built from `goal` + `context` ([delegation](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation)).
- **Batch/parallel:** up to 10 concurrent children by default; optional `output_schema` per task (JSON Schema, one bounded correction turn, `schema_valid`/`schema_errors` on the result); background completions are durable events in `state.db` (crash-safe delivery, at-least-once) and return as a synthetic new turn.
- **Nested orchestration:** `role="orchestrator"` children keep the delegation tool, bounded by `delegation.max_spawn_depth` (default 1 = flat); child-blocked tools prevent privilege escalation.
- **Operational polish:** live per-task transcripts, steering (`list`/`steer`/`stop`), progress-based stall detection (never a wall-clock kill for healthy long children), structured timeout metadata, per-child model pinning (`delegation.model`, e.g. frontier planner + cheap workers), and `/review` (independent reviewer subagent on the same background rail).
- **Kanban is the durable multi-task counterpart** ([kanban](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban)): a board of cards with dependencies, assignees, per-task model override, worker processes under systemd scopes, goal-mode cards reusing the Ralph loop, and orchestrator vs manual dispatch — for work that must survive restarts.

## Approvals / security

- **Eight documented layers** ([security](https://hermes-agent.nousresearch.com/docs/user-guide/security)): user authorization, dangerous-command approval, file-write safety, container isolation, MCP credential filtering, context-file injection scanning, cross-session isolation, input sanitization.
- **Approval modes:** `smart` (auxiliary LLM risk-assesses each command; low-risk auto-approve, dangerous auto-deny, uncertain → prompt), `manual`, `off`. Per-surface headless policy: `cron_mode`, `single_query_mode`, `unattended_mode` all default to **deny** where no human can answer; an expired prompt fails closed.
- **A hardline blocklist sits below YOLO** (rm -rf /, fork bombs, mkfs on root device, dd to block device, pipe-to-shell at rootfs) — no override flag. User-editable `approvals.deny` glob rules are checked before YOLO/off; a permanent `command_allowlist` records "always" approvals, and `hermes approvals suggest` mines approval history into proposals (destructive classes never proposed).
- **File writes:** protected-path denylist (SSH/AWS/kube/sudoers/Hermes secrets, `.env` read-denied), optional `HERMES_WRITE_SAFE_ROOT` hard sandbox, MCP/terminal env sanitizer (safe-var allowlist; skill-declared env vars and credential files pass through explicitly), SSRF protection and a website blocklist for URL-capable tools. Docker runs `--cap-drop ALL`, `no-new-privileges`, pids/tmpfs limits. A supervised-gateway guard stops the agent killing/restarting its own gateway, regardless of YOLO.

## Voice / STT / TTS

- **STT:** local Faster-Whisper (no key), Groq, OpenAI, Mistral, xAI, ElevenLabs; file + streaming providers; auto re-encode/split of long audio; hallucination filter for Whisper phantom phrases; voice notes transcribed on messaging platforms; `/voice` modes (`off`/`voice_only`/`all`).
- **TTS:** Edge (free), ElevenLabs, OpenAI, NeuTTS, Piper, MiniMax, Mistral, Gemini, xAI; **streaming TTS** speaks sentence-by-sentence as the model generates; `text_to_speech` and `[[audio_as_voice]]` deliver native voice bubbles.
- **Voice UX:** Ctrl+B push-to-talk with VAD silence detection, continuous loop, barge-in (talking over a reply interrupts it), stop phrases, wake word, Discord voice channels (bot joins VC, listens per-user, speaks back), a `voice_chat` auxiliary model slot (reasoning off by default), and Desktop client-direct voice that bypasses the gateway relay ([voice mode](https://hermes-agent.nousresearch.com/docs/user-guide/features/voice-mode)).

## Desktop / UI

- **Electron desktop app + React chat surface**, talking to the profile's gateway over `/api/ws` with one-use tickets; remote gateways (URL/SSH/Tailscale/Hermes Cloud) and a multi-connection registry ([desktop](https://hermes-agent.nousresearch.com/docs/user-guide/desktop)). The **TUI** is an Ink app backed by `tui_gateway/` (Python JSON-RPC), which also serves Desktop; the web dashboard embeds the real TUI; **ACP** exposes the agent to editors; an **API server** and **webhooks** expose it to scripts.
- **Bot Mode turns profiles into a roster of named Bots** ([bot mode](https://hermes-agent.nousresearch.com/docs/user-guide/bot-mode)): each Bot = a Hermes profile (own config/memory/skills/credentials/avatar/voice), one permanent canonical "Bot Chat", per-Bot **Routines** (plain cron jobs namespaced `[bot:<name>]`), group chats of 2–6 Bots with @mentions and a durable room driver, bot-to-bot `message_agent` with hop limits, and `hermes peer` for gateway-to-gateway messaging without a Desktop in the loop. This is the strongest "personal assistant OS" surface in the product.

## Sessions / state

- **Every conversation is a session in `state.db`** with title, source platform, model, system-prompt snapshot, full messages/tool calls, token counts, parent session (compression lineage), and routing identity ([sessions](https://hermes-agent.nousresearch.com/docs/user-guide/sessions)).
- **Compression creates child sessions** (`"my project" → "my project #2"`); memory is flushed before compression; the last N messages and tool pairs are protected; prompt-cache prefixes are preserved except at deliberate boundaries.
- **Continuity features:** resume by id/title/terminal breadcrumb, cross-platform `/handoff` (CLI → Telegram thread etc.), session search, export (jsonl/md/html/trace), prune/archive/pin, and repair tooling for stranded gateway sessions. Prompts are pinned per session, with `hermes sessions refresh-prompts` to adopt edited `SOUL.md`/skills/context files at one cache-miss cost.
- **Profiles are islands:** each `hermes -p <name>` gets its own `HERMES_HOME`, config, memory, skills, credentials, sessions, and gateway; one multiplexing gateway can serve many profiles.

## Model routing

- **A shared runtime resolver** maps `(provider, model)` → `(api_mode, api_key, base_url)` across 18+ providers, OAuth flows, credential pools, and aliases — used by CLI, gateway, cron, ACP, and auxiliary calls ([provider runtime](https://hermes-agent.nousresearch.com/docs/developer-guide/provider-runtime)).
- **Fallback chains** per profile and per route (`fallback_providers`), with credential refresh on 401/403 and a Codex "reasoning-only stall" fallback rule.
- **Auxiliary model slots** for side tasks: vision, compression, skills_hub, approval, mcp, title generation, triage, kanban decomposer, profile describer, curator, web_extract, session_search, flush_memories, goal_judge, review, voice_chat, background_review — each independently routable to a cheap/fast model. Local `config.yaml` shows the full 13-slot `auxiliary:` block plus per-surface `model`/`provider` overrides for delegation and cron.
- **OpenRouter provider routing** (`sort: price|throughput|latency`, allow/ignore lists, per-model pins, `data_collection: deny`) and prompt-cache TTL controls sit on top.

## Why it feels like a personal assistant

1. **Chat-first, always-on identity.** A long-lived gateway plus a persona file (`SOUL.md` is slot #1 of the system prompt) means it has a stable voice and is reachable from whatever app you already use — not a tool you open, an entity you message.
2. **It remembers you across sessions**, in a bounded way you can inspect and correct: two curated memory files, a user profile, FTS5 search over everything ever said, plus optional external memory backends.
3. **It acts without being asked.** Cron with delivery targets, heartbeats inside a live thread, goals that keep working across turns, background subagents that report back, kanban workers for multi-day work.
4. **It gets better at your job.** Skills authored from experience, a curator that prunes/consolidates them, usage telemetry, and a visible "learning journey" — the self-improvement loop is the product.
5. **It is allowed to do real things.** Terminal/browser/desktop control, credentials, MCP tools, with a layered approval system scaling from "ask me every time" to headless deny-by-default for unattended runs.
6. **It lives where you do.** Telegram/Discord/Slack/WhatsApp/Signal/email/SMS/voice, a desktop app with bots and group chats, editor ACP, and an API for scripts — same agent, same memory, same sessions.

## Lessons for DSH

Mapping Hermes subsystems to what DSH 0.2.2-rc.1 already ships (from the local `@deepseek-ai/*` package inventory: `dsh-schedule`, `dsh-goal`/`dsh-goal-round-driver`, `dsh-tool-ralph`, `dsh-experimental-agent-team`, `dsh-subagent*`, `dsh-mcp-client`, `dsh-tool-skill`, `dsh-session*`, `dsh-compaction*`, `dsh-client-ui-approval`, `dsh-experimental-voice-input`/`speech-to-text-sensevoice`, `dsh-api-remote-access`, `dsh-host-webserver`) to gaps:

1. **Messaging gateway is the single biggest gap.** Hermes' product feel comes from 25+ chat adapters in one long-lived process with per-platform authorization, home channels, and delivery. DSH has a web GUI and remote API but no IM channel layer — a plugin-shaped gap (adapter interface + session routing + allowlist/pairing + delivery), not a core rewrite.
2. **Bounded, agent-editable memory injected as a frozen prompt block.** DSH has session persistence but no memory subsystem. A 2–3 KB `MEMORY.md`/`USER.md` pair with `add/patch/remove`, capacity errors that force consolidation, injection scanning, and staged writes is a small, high-leverage plugin.
3. **Scheduling needs delivery + durability, not just timers.** DSH ships `schedule_*` tools; Hermes shows the rest: delivery targets, an execution ledger with claimed/running/terminal states, pre-dispatch config validation (never spend tokens on a broken job), failure incidents, catch-up windows, per-job model pins.
4. **Separate "heartbeat" from "cron".** A recurring prompt injected into the *current* session when idle (cache-safe, context-aware) is a different primitive from a fresh-session scheduled job. DSH's `dsh-tool-ralph`/goal driver is adjacent; a session heartbeat is cheap to add and makes the agent feel present during long work.
5. **Goals: add completion contracts and deterministic gates.** Hermes' `/goal` judge is fallible; the contract (`outcome/verification/constraints/boundaries/stop_when`) plus shell-command quality gates run *before* the judge is what makes "done" checkable. DSH has `dsh-goal`; the contract+gate layer is the missing rigor.
6. **Skills need a lifecycle, not just a loader.** DSH has `dsh-tool-skill`; Hermes adds progressive disclosure (index → full → reference), `/skill` + bundles, agent-authored skills via a manage tool, usage telemetry, a curator (stale/archive/consolidate), and a scanned Hub with trust tiers. The curator + telemetry are what keep a growing skill library from rotting.
7. **Subagent durability and control.** DSH has in-process `dsh-subagent`; Hermes' differentiators are durable background completions (state.db events, crash-safe delivery), `output_schema` contracts, steering/stop, per-child model pins, and progress-based stall detection instead of wall-clock kills.
8. **A durable task board is worth more than deeper nesting.** Kanban (cards, dependencies, per-task model, worker processes) handles multi-day, restart-surviving work that in-process delegation cannot. DSH's agent-team packages could grow a board/queue surface rather than only concurrent teammates.
9. **Approvals must be per-surface, not global.** DSH has an approval UI; Hermes' key insight is `cron_mode`/`single_query_mode`/`unattended_mode` defaulting to deny where no human can answer, plus a hardline floor below YOLO and a user-editable deny-glob list. Without per-surface policy, scheduled agents either stall or get blanket approvals.
10. **Route side tasks to cheap models via named slots.** Title generation, compression, memory review, curator, goal judge, session search, and voice turns should not run on the frontier model. DSH has model selection; a per-task auxiliary routing table (and per-surface pins for scheduled/delegated work) is the cost lever.
11. **Profiles-as-bots is a cheap product win.** Hermes Bot Mode is just profiles + a canonical chat + routines + a roster UI; DSH already has profiles/agent-team-profile packages. A "bot roster" surface with per-bot memory/skills/model and one permanent conversation turns a coding harness into something that feels like an assistant.
12. **Plugin/skill distribution needs supply-chain trust.** Hermes' catalog is human-merged YAML with mandatory SHA pins, security scanning, trust tiers, and a removal kill list. DSH's 330-package plugin ecosystem will need the same admission rules (pins, scans, provenance) before third-party plugins become safe to recommend.
